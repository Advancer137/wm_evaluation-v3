# PreferenceWorldBench 视频盲评界面

这是一个 Python 本地网页服务，后端使用标准库；视频兼容处理使用项目 `vendor` 中的 FFmpeg。正式数据从同级 `data_source` 自动关联、检查并生成固定评测题库。不带参数的 `serve` 仍运行模拟演示，演示答案不纳入正式导出。

## 推荐入口：管理界面

Windows 下双击 **`启动管理界面.cmd`**，浏览器自动打开 `http://127.0.0.1:8766/`。需要 Python 3.10 或更高版本，并让启动窗口保持运行。也可以运行 `python server.py manage --open`。

管理界面分为三个页面：

1. **组织评测**：按“主电脑准备并分发评测包 → 每台电脑本地作答 → 人工收集文件”组织。主电脑检查数据、创建评测题库、按编号分配并生成各编号的评测包；学生不使用管理界面，直接双击评测包里的 `启动评测.cmd`。本页第 2 步仅供组织者在本机试答。程序自动选择本机端口，无需配置网络。作答后可查看本机结果文件的完整路径和更新状态。
2. **题目与作答**：选择输入数据可查看全部基础题目及已找到的视频（包括素材不完整的题目）；选择固定题库则显示该题库所有题目及已汇入的作答。可按 case、模型、track 搜索筛选。详情固定显示原始 A/B 视频、模型、版本、声明的方法、seed、domain、index，独立答案同时显示原始 X/Y 映射和恢复后的 A/B 判断。点击“加载 / 刷新”获取最新作答。
3. **结果汇总**：选择题库，下载本机结果或多选其他电脑收集来的 JSON 文件导入，再点击“更新汇总”。同题库本机答案会自动纳入。可下载含逐题原始答案、共识与分组统计的 ZIP。

管理服务只监听本机 `127.0.0.1:8766`，由管理界面启动的评测服务也仅允许本机访问（自动选择 8767–8787 中可用的端口）。志愿者服务在单独的端口上运行，不提供管理页面或管理 API。管理页面不会出现在志愿者导航中。管理窗口关闭或服务进程退出后，它开启的志愿者服务也会停止；重启后选择同一题库即可继续，原数据库不变。

部分输入 MP4 使用 `mp4v`（或 HEVC、10-bit 等）编码，浏览器不能直接播放。创建题库时程序用 FFmpeg 读取每个视频的编码（`ffmpeg -i`）：已经是 **H.264 + yuv420p** 的原样使用；其余的转成 **H.264 高质量副本（CRF 18，视觉上无损，约为旧版 VP9 无损副本的 1/5 以下）**，并固定、校验在题库内，原始文件及其路径保留用于核对。如果所用 FFmpeg 没有 libx264，会自动改用 VP9（CRF 20）。视频不裁剪、不改变帧率；音轨转为 AAC。当前项目附带 `imageio-ffmpeg 0.6.0` 的 Windows x64 FFmpeg（已确认含 libx264）；其他系统需自行安装 FFmpeg。已创建的旧题库（VP9 无损副本）不受影响，仍可使用；要减小体积请用同样的数据创建新题库。

### 参考译文（可选）

在 `data_source/question_base/` 放一个 `translations_zh.tsv`，评测页就会在共同条件、偏好 A、偏好 B 的英文原文下方显示灰色的“参考译文”，原文不变；页面会提示“如与英文原文不一致，请以英文原文为准”，志愿者可用右上角按钮隐藏/显示译文（按浏览器记住）。

- 文件格式：UTF-8 的两列 TSV，`英文原文<Tab>中文译文`，第一行可以是表头 `source<Tab>zh_reference`。按英文原文匹配（忽略多余空格），与行的顺序无关，可用 Excel 编辑后另存为“文本文件（制表符分隔）/UTF-8”。
- **没有这个文件也完全不影响使用**：检查数据时找不到它，参考译文功能就关闭，评测页不出现任何译文元素。
- 有文件时，“检查数据”会做初步核对并在报告中列出：格式不对的行、空译文、不含中文的译文、原文数字未出现在译文中、同一句的冲突译文、没有译文的题目文本。有问题的单条译文不显示（数字不一致只提醒），不会阻止创建题库。若文件读不出来、大部分行格式错误、或与题目文本完全对不上，则整体关闭该功能。
- 译文在创建题库时固定进 `tasks.jsonl`（随题单一起校验），保证所有作答者看到同一版译文；修改译文后需重新创建题库。管理页“题目与作答”详情里同样显示译文。

### 多台电脑独立运行与汇总（按编号预先分配）

**核心做法：每台评测电脑一个编号（A01、A02…），组织者在主电脑上一次性分好题、分别打包。**

1. **主电脑创建题库**（“01 组织评测”第一块）。创建完成后不再自动生成完整大包。
2. **分配并打包**：选择题库，填写“评测电脑数 / 标注人数”和“每题份数”（默认 10 人、每题 3 份；每题份数不能大于人数，因为同一道题必须由不同的人做），点击 **生成分配并打包**。系统会：
   - 均衡分配：每道题分给不同的 `每题份数` 个编号，各编号题数相差不超过 1，同一个编号尽量不连续看到同一 source case 的题；
   - 提前固定每人每题的 X/Y 顺序（同一题的几份标注里 X/Y 两种顺序都会出现），因此分配可复现；
   - 为每个编号单独生成 `evaluation_packages/<题库>/<方案编号>/evaluation-<题库>-A01.zip` 等。**包里只含该编号要看的视频和图片**（不含原始 mp4v 文件、不含别人的题目素材、不含管理界面），体积小。方案文件保存在 `batches/<题库>/plans/<方案编号>.json`，请留存（汇总时用来核对）。
   - 随机种子留空即自动生成；种子、人数、份数相同则得到同一个方案。方案生成后可在“已有分配方案”里重新打包或再次下载。
3. **学生端**：把各编号的 ZIP 发给对应电脑。学生解压后只需双击 **`启动评测.cmd`**（使用电脑里已有的 Python 3.10+，不打包 Python）。它只启动答题页，固定在 `http://127.0.0.1:8780/` 并自动打开浏览器，没有管理界面、看不到题目与 A/B 对应关系。包里还有 `学生说明.txt`。如果评测窗口已经开着，再双击会直接打开浏览器页面。
4. **断点续答**：每个包就是一个人。题单固定，已作答的题保存在本机数据库；退出后再次双击启动、输入**同一姓名**，就回到下一道没做的题。即使换了浏览器或清除了浏览器数据也一样（身份由编号决定，不靠浏览器记录）；输入别的姓名会被拒绝，提示该包已由谁使用。注意：尚未提交的半填答案仍只存在原浏览器里（原有行为）。
5. 每次提交或修改答案后，自动更新 `../evaluation_results/<题库>/results-<编号>-<姓名>-<设备ID>-<标识>.json`。全部做完时页面会显示这个文件的完整路径，请学生把它发给组织者；之后若改了答案，需发送最新文件。
6. **汇总**：在主电脑“03 结果汇总”页选择题库，一次选择所有收集到的 JSON 文件导入。导入时会按分配方案核对：不在该编号清单里的题、X/Y 与方案不一致的记录会让整份文件被拒绝（不会部分写入）；同一编号从两台电脑来的文件会按答案版本合并成一份，不会重复计票；找不到方案文件时仍可导入但会给出提示。

**进度总览与导入报告**（“03 结果汇总”第 2 块，导入后自动刷新，也可手动点“刷新进度”）：
- 各编号：姓名、完成/计划题数、状态（未收到 / 进行中 / 已完成）、最近提交时间、来源电脑；
- 份数不足的题目：每题已有/需要几份，以及还缺哪些编号的答案；
- 提示：尚未收到或未做完的编号、同一姓名出现在多个编号（可能重复领包）、同一编号来自多台电脑、不属于方案的作答者、被拒绝的导入；
- 导入记录：每次导入的时间、文件、结果或拒绝原因。

“更新汇总”仍计算共识与严格 SBPS，导出的 `raw_annotations.jsonl` 多了 `slot`、`plan_id` 字段。合并数据单独保存在 `merged.sqlite3`，不会修改各电脑的原始作答。

**旧流程（不预分配）仍保留**：管理页“高级：生成完整分发包”会生成含全部视频与管理界面的大包，各电脑随机抽题（`--target-per-task`、`--tasks-per-volunteer`），不保证每题份数，身份靠浏览器记录；仅作调试或兼容使用。请不要把答过题的整个目录（尤其 `annotations.sqlite3`）当作新电脑的初始包。

**从已有结果开始（校验或补做）**：管理页“02 在这台电脑开始评测”里展开“从已有结果开始（可选）”，选择一个结果 JSON，再点“启动本机评测”。文件中与本题库内容相同的题（规则同下面的跨题库兼容）会作为一位新作答者的已保存答案导入，作答者姓名取自文件；X/Y 顺序沿用原文件。点“打开志愿者界面”后输入该姓名，页面直接打开第一道已导入的题，可用“上一题 / 下一题 / 跳转题目”逐题查看、修改后点“保存修改”；文件里没有的题（例如新题库新增的题）点“继续评测”照常作答。此时每人题数上限自动放宽到题库总题数。导出的结果文件就是这位作答者校验后的版本；原始结果文件若只是草稿，汇总时不要再一起导入，以免重复计票。

**跨题库兼容（增删题目后旧结果仍可用）**：题目的编号由“模型 + track + case + 版本 + seed”决定，与题库无关；每道题另有一个“内容指纹”，由上述信息、共同条件与偏好 A/B 的英文原文、**原始**视频 A/B 的校验值组成（不含播放副本和参考译文，所以换转码方式、改译文不影响）。把旧题库的结果文件导入新题库时：
- 与当前题库指纹相同的文件照常导入；不同时按题逐条核对，只计入内容指纹完全相同的题，X/Y 映射原样沿用；
- 新题库里已删除的题、编号相同但内容变了的题（改了英文条件措辞、重新生成了视频）不计入，导入结果和导入记录里会列出各有多少条；
- 只是初始帧不同（例如后来补充了初始帧）的题仍然计入，并单独提示条数；
- 新版本导出的结果文件每条记录都带内容指纹，不需要旧题库也能核对；更早格式的文件（没有内容指纹）需要它对应的旧题库文件夹仍在 `batches/` 下，程序会自动找到它；
- 旧题库分配方案下的编号答案计入题目份数，进度总览中显示为“其他方案”的作答者。

A/B 映射冲突、未知格式、同一版本答案冲突仍会整份拒绝，不会静默合并。

独立电脑的每题目标份数分别计算，合并后可能超过目标，界面会显示实际数量。汇总时按多数共识计算，少于三份答案的题目不进入严格 SBPS 的分母，并列入待复核。统计属于描述性汇总，不包含跨模型配对抽样或显著性检验。

以下命令行方式仍可使用。`aggregate --batch` 导出的是该题库本机数据库；多机合并请使用管理界面的结果汇总。

## 立即预览

在 `evaluation_base` 目录运行：

```powershell
python .\server.py serve
```

浏览器打开 `http://127.0.0.1:8765`。演示画面是可重播的模拟动画，主要用于检查页面和提交流程。开始前填写姓名；系统生成独立会话 ID，刷新后可继续任务。同机换人时返回首页，勾选“另一位作答者”，填写新作答者姓名。姓名用于文件整理，不作为自动去重依据。

## 正式评测：放数据 → 检查 → 创建评测题库 → 启动

### 1. 放置数据

```text
WMpreference/
├── evaluation_packages/  # 自动生成的分发 ZIP
├── evaluation_results/   # 按题库、姓名保存的作答结果
├── evaluation_base/
│   └── server.py
└── data_source/
    ├── input_config.json                 # 可选：版本与 raw/AlignX 的明确对应
    ├── question_base/
    │   ├── final_valid_conditions.jsonl  # 或 JSON 数组文件
    │   └── images/
    │       └── <图片名>.jpg
    └── question_video/
        └── <模型名>/
            └── <track>/
                ├── WMB_0052__A__policy_v3.mp4
                └── WMB_0052__B__policy_v3.mp4
```

默认数据位置始终按 `server.py` 所在目录定位，与终端当前路径无关。以下命令在 `evaluation_base` 目录执行。

基础信息使用 UTF-8（支持 BOM）。JSONL 每行一个对象，JSON 顶层为对象数组。`question_base` 中应有且仅有一个 JSON/JSONL 文件；如果有多个，通过 `--metadata final_valid_conditions.jsonl` 明确选择。

| 页面／关联信息 | 元数据字段 |
|---|---|
| 共同条件 | `base_condition.text` |
| 偏好 A | `preference_condition_A.text` |
| 偏好 B | `preference_condition_B.text` |
| 首帧 | `first_frame`，例如 `images/abc.jpg` |
| 唯一关联键 | `source_case_id + track` |
| 后台元信息 | `index`、`domain` |

`first_frame` 可省略、设为 null 或空字符串；填写时必须是指向 `question_base/images` 内的相对路径；旧的绝对 `image_path` 不参与导入。必填文本字段缺失、重复关联键、路径越界或 JSON 解析错误会阻止创建评测题库。

视频路径格式为 `<模型>/<track>/<case>__<A或B>__<版本>.mp4`。版本名按原样保存，例如 `raw_prompt`、`policy_v1`、`policy_v3`；模型名称也原样保存，名称中的 `stage3` 不会被当作 AlignX 版本。若同条件生成多个 seed，命名为：

```text
WMB_0052__A__policy_v3__seed_42.mp4
WMB_0052__B__policy_v3__seed_42.mp4
```

按 **模型 + track + case + 版本 + seed** 分组寻找 A/B；绝不跨组配对，也不自动选择“最新版本”。无 seed 的文件保存 `generation_seed=null`，不会假设为 0。有 seed 与无 seed 也不会互相配对。当前不支持额外题库子目录；需要重复实验时使用明确 seed 或通过下方高级 manifest 接口提供独立 `task_id`。

版本后缀不直接证明生成方法。可将 `evaluation_base/input_config.example.json` 复制为 `data_source/input_config.json`，根据真实生成记录填写 `variant_methods`，值允许 `raw`、`alignx` 或 `null`。示例中的 policy 版本保持 `null`，确认后再改成 `alignx`。未填写时 `method=null`，报告会提醒，但仍可按原始版本名开展评测；这些字段只保存在后台。

服务器原有 `manifest.jsonl`、`missing.jsonl`、`summary.json` 尚未确认字段定义，因此本接口不会自动解析它们。模型目录下的非 MP4 文件不作为视频；不符合上述命名或层级的 MP4 会列入报告。

### 2. 检查数据

```powershell
python .\server.py check-data
```

生成 `reports/input_check.md`（可读报告）和 `reports/input_check.json`（完整结构化报告）。列出可用数量、缺少首帧、缺少 A/B、找不到基础信息、重复记录和未声明方法的版本。检查文件存在且非空，不进行视频解码或内容质量评判。

初始帧缺失、空文件或整个 images 目录未提供，仅记录警告，不阻止题目入库；评测页面显示“未提供初始帧”。缺配对和孤立视频对应的题目仍会排除。已提供的初始帧仍会复制并校验；路径越界或格式错误不会当作缺图忽略。请先核对报告中的排除项，因为缺失数据会影响实际评测覆盖范围。没有任何可用题目或存在致命错误时不允许创建评测题库，`check-data` 返回非零退出码。

### 3. 创建评测题库

```powershell
python .\server.py prepare --batch study-001
```

自动生成 `batches/study-001/`，其中包含：

- `tasks.jsonl`：固定的题目文本、A/B 视频关联和后台元信息；
- `media/`：该题库用到的图片和视频副本，同一首帧只复制一次；
- `snapshot.json`：题单和媒体的 SHA-256 校验值及来源记录；
- `input_check.md` / `input_check.json`：创建时的检查报告；
- `annotations.sqlite3`：第一次启动该题库时创建，单独保存作答。

复制媒体会占用额外磁盘空间，大小约为该题库选中媒体的总大小。题库名不能覆盖；失败不会留下半成品题库。修改或增加 `data_source` 中的文件不影响已创建的题库，新数据应创建 `study-002` 等新题库。

### 4. 启动、继续和导出

```powershell
python .\server.py serve --batch study-001
```

打开 `http://127.0.0.1:8765/`。若旧演示服务仍占用该端口，先在旧服务终端按 Ctrl+C，或给新服务指定 `--port 8766`。

重启时使用相同命令，即继续原题库和数据库。启动前自动校验题单及所有媒体；文件被修改或丢失时拒绝启动。运行期间也检查媒体大小和修改时间，检测到变化则拒绝提供该媒体。请不要直接编辑题库目录里的题单和媒体。

导出当前题库：

```powershell
python .\server.py aggregate --batch study-001
```

结果位于 `batches/study-001/export/`。如需其他输入目录，给 `check-data` / `prepare` 指定 `--source <目录>`；如需选择元数据文件，给它们指定 `--metadata <文件名>`。`--batch` 启动自动选择固定媒体和数据库，不能同时指定 `--manifest`、`--media-root` 或 `--db`。

## 高级接口：直接加载规范化 manifest

准备 UTF-8 JSONL，每行是一对视频的一个任务：

```json
{"source_case_id":"WMB_0000","index":0,"domain":"autonomous vehicle","track":"risk","base_condition":"A vehicle approaches an intersection.","preference_a":"Stop before entering the intersection.","preference_b":"Continue through the intersection.","initial_frame":"frames/WMB_0000.jpg","video_a":"videos/opaque_001.mp4","video_b":"videos/opaque_002.mp4","world_model":"private_model_name","stage":"raw","generation_seed":42}
```

- `initial_frame`、`video_a`、`video_b` 是相对于 `--media-root` 的路径。服务端通过 `/media/<opaque-task-id>/frame|x|y` 提供文件，志愿者看不到原始文件名。
- `world_model`、`stage`、`generation_seed` 及其他额外字段只保存在后台，不进入标注页面的任务 JSON。服务器会把显式提供的 `task_id` 或 case、track、model、stage、seed 组合哈希为稳定的不透明 ID。`domain`、`track` 和原始 case ID 也只用于后台汇总；志愿者仅看到中性样本编号，以免被类别信息提示。
- `prepare` 已自动完成这些字段的转换。高级接口供其他生成流程直接提供明确的视频路径、stage、model 和 seed；直接使用 manifest 不会自动复制媒体或生成校验快照。
- 同一 `source_case_id × track × world_model × stage × generation_seed` 应对应一行。若以后需要多个重复任务，显式提供不同的 `task_id`。
- 避免在公开字段中写入模型或方法名称。服务端会保存 X/Y 与原始 A/B 的隐藏映射，且每个志愿者的映射保持不变。

启动正式任务时使用**新的数据库文件**：

```powershell
python .\server.py serve --manifest .\tasks.jsonl --media-root D:\review_media --db .\study.sqlite3
```

日常评测请使用上方管理界面的本机流程；各电脑独立保存答案，由组织者收集结果 JSON。

## 标注与导出

页面要求先看示例并确认规则。每个任务显示第一帧、共同条件、偏好 A/B、匿名 Video X/Y。X/Y 在服务器分配任务时随机交换，刷新不会改变。每段视频分别标记：

1. **视频有效性**：有效 / 损坏或无法播放 / 证据不足。只看技术上能否评测；动作做反、时间倒放属于内容问题，仍选“有效”。选后两者，该视频后面的问题全部跳过。
2. **基础任务**：共同条件描述的事件完成到什么程度（完成 / 部分完成 / 未完成 / 无法判断）。完成：共同条件里的动作和结果都出现了，缺前置步骤或有画面瑕疵不影响；部分完成：方向、主体正确，事件明显开始，但缺后半或结果（如只跑没跳、只缠绕没压碎）；未完成：动作没发生、做反或倒放、做成别的事，或视频基本静止。**只有“未完成”不再询问偏好 A/B，汇总时两项偏好都按“否”计；“完成”和“部分完成”都要回答偏好。**
3. **共同条件保持**：与初始画面相比，主体与场景是否保持一致（保持 / 未保持 / 无法判断）。选“未保持”时必须勾选原因（可多选）：主体不一致、场景不一致、视角/镜头突变、其他，并可附一句说明。该题只比较一致性，与基础任务是否完成无关。
4. **是否呈现偏好 A / 偏好 B**：是 / 否 / 无法判断，作为一个整体答案，只依据画面里已经出现的内容：相符且无矛盾选“是”；与偏好矛盾选“否”；已出现的内容不足以判断（偏好说的恰恰是没出现的部分，或看不清）才选“无法判断”。事件没做完不是选“无法判断”的理由，完成度已由第 2 题单独记录。视频质量（穿模、画面不自然）本身不改变答案，除非它让所需的画面看不清。

答案文件里，被跳过的问题保存为 `null`（原始作答保持原样），汇总时再按上面的规则换算。结果文件格式为 `pwb-results-v2`；仍可导入旧的 `pwb-results-v1` 文件。**旧题目集的答案保持原样导入**，其中的偏好和有效性照常计入，但没有基础任务答案，旧的“场景与共同事件”也不并入新的“共同条件保持”。在作答界面重新打开这样的旧答案会提示补答新增的两问。

不同志愿者独立作答；每条任务默认目标为 3 份标注，每位志愿者默认最多完成 30 对。可用 `--target-per-task`、`--tasks-per-volunteer` 调整。服务器优先分配已完成标注较少的任务，并尽量避免连续出现同一个 source case。已经分配但尚未提交的任务会保留给该志愿者，因此同时在线或中途退出时，个别任务可能超过或暂时不足 3 份标注，导出后应检查 `annotation_count`。

页面上方的“上一题 / 下一题 / 跳转题目”可以返回此前分配给自己的任意题目。“继续评测”返回待答题目或领取下一题。已提交的题目会回填自己的答案，修改后点击“保存修改”；即使已完成整轮评测，也能从完成页上方导航回看。视频 X/Y 的顺序始终保持不变。每人每题始终只计一份标注，聚合使用最近保存的答案。

未提交或未保存的选择会在切换题目时保留，并作为草稿暂存于当前浏览器；导航中的“草稿未提交”提醒这些选择尚未进入正式结果。关闭前请提交或保存修改。返回历史题目需要使用原来的浏览器配置，不要清除浏览器的本地存储。

完成后停止服务，运行：

```powershell
python .\server.py aggregate --db .\study.sqlite3 --out .\export
```

得到 `raw_annotations.jsonl` 和 `consensus.jsonl`。后者把 X/Y 标签恢复为真实 A/B 标签，逐项采用过半数且至少两人一致的规则；三人各选不同标签时偏好、基础任务与共同条件共识记为 `uncertain`，并列入仲裁。`strict_sbps` 对有效视频的四项偏好计算（基础任务未完成的视频，偏好按“否”计），`uncertain` / 损坏视频按失败处理；少于三人时留空。**目前主指标 `strict_sbps` 不加门槛**（完成与部分完成的视频都按偏好模式计入，未完成的视频因偏好为“否”自动失败）；`consensus.jsonl` 另给出 `strict_sbps_task_done`（再要求两段视频的基础任务共识都是“完成”）、`strict_sbps_with_gates`（再要求共同条件共识为“保持”）、`base_task_counts`（各视频基础任务各档的人数）和 `retention_reasons`（“未保持”原因计数），管理界面的汇总里也有对应的三个通过率，供之后按严格程度选用。**完整的人评统计、Judge 校准划分与显著性检验尚未纳入这个界面**；后续应按研究方案以 `source_case_id` 为单位完成分析。
